# Cài Valley Chibi Studio trên Cloudflare từ GitHub

Đây là bản Workers độc lập: giao diện + API + Remote MCP cùng một Worker, D1 lưu dự án/đầu việc, Workers KV `FILES_KV` lưu file, KV `OAUTH_KV` lưu phiên đăng nhập và OAuth. Bản mặc định dùng được với Workers Free trong hạn mức, không cần R2. Giữ đầy đủ storyboard ảnh ChatGPT, thư viện Reference, Dark Mode và chibi 3D.

## 1. Chọn đúng nơi trong ảnh Cloudflare

Workers & Pages → Create application → Continue with GitHub → chọn repo vanhungtq/valley-chibi-studio.

Dùng nhánh main. Không chọn Continue to Pages hoặc Upload static files: app cần Worker API và MCP.

Root directory: /
Build command: npm run build:cloudflare
Deploy command: npm run deploy:cloudflare
Node.js: 24 (đặt NODE_VERSION=24 trong Build variables nếu cần)

Nếu dùng Deploy to Cloudflare button, Cloudflare có thể sao chép repo sang một repo mới. Muốn cập nhật chính repo của bạn thì dùng Continue with GitHub ở trên.

## 2. Lưu trữ và migration

wrangler.jsonc khai báo:
- D1 binding DB — database mặc định valley-chibi-studio.
- KV binding FILES_KV — nội dung tệp riêng theo tài khoản, tối đa 20 MiB/tệp.
- KV binding OAUTH_KV — dữ liệu OAuth và phiên đăng nhập.
- Assets binding ASSETS — thư mục public/.

Script `npm run deploy:cloudflare` kiểm tra tài nguyên trong tài khoản Cloudflare đang xác thực trước khi deploy. Khi cấu hình chưa có ID, script dùng lại D1 có đúng `database_name` và KV có đúng tên mặc định của Wrangler: `valley-chibi-studio-oauth-kv` và `valley-chibi-studio-files-kv`. ID được gắn vào cấu hình trong môi trường build; không tự commit lên GitHub. Vì vậy, retry sau lần deploy lỗi vẫn dùng đúng kho đã tạo, tránh lỗi KV `10014` (namespace cùng tên đã tồn tại). ID đã khai báo được giữ nguyên. Nếu không đọc được danh sách tài nguyên, script dừng và giữ thông báo lỗi, không coi đó là kho chưa tồn tại.

Wrangler chỉ provision các binding vẫn chưa có tài nguyên. Cấu hình không còn `r2_buckets`, nên không có bước tìm hoặc tạo R2 bucket. Với kho đặt tên riêng, điền database_id/id thực tế vào đúng binding trong wrangler.jsonc. Không dùng ID của tài khoản khác. Không xóa namespace OAuth để xử lý lỗi trùng tên.

Nếu muốn tạo bằng giao diện giống ảnh đã gửi: Storage & databases → Workers KV → Create namespace. Tạo kho tệp và kho OAuth riêng; trong binding của Worker, dùng đúng tên biến `FILES_KV` và `OAUTH_KV`. Ghi ID namespace thực tế vào `wrangler.jsonc` để các lần deploy tiếp theo dùng cùng kho:

```json
"kv_namespaces": [
  {"binding": "OAUTH_KV", "id": "ID_NAMESPACE_OAUTH_CUA_BAN"},
  {"binding": "FILES_KV", "id": "ID_NAMESPACE_FILES_CUA_BAN"}
]
```

Free KV có 1 GB lưu trữ, 100.000 lượt đọc/ngày, 1.000 lượt ghi/ngày, 1.000 lượt xóa/ngày và 1.000 lượt list/ngày, dùng chung toàn bộ tài khoản. Khi hết hạn mức, thao tác bị từ chối. Kiểm tra usage trong Dashboard; không coi đây là kho video không giới hạn. Mức của ứng dụng là 20 MiB/tệp, thấp hơn trần 25 MiB/value của KV. File Codex nộp qua MCP vẫn tối đa 1 MiB/file, đọc MCP tối đa 5 MiB/lượt.

KV có thể cần 60 giây hoặc hơn để dữ liệu hiện ở khu vực khác; đọc thiếu tệp mới cần thử lại, không suy đoán nội dung. Giao diện thử tải lại ảnh mới có giới hạn. Video được phục vụ theo byte range nhưng KV đọc nguyên giá trị phía máy chủ, nên video gốc dung lượng lớn nên lưu bằng URL và ảnh shot. Trạng thái dự án, claim và duyệt vẫn ở D1 để giữ kiểm soát đồng thời.

Nếu đã có file trong R2, bản này không tự copy hoặc xóa chúng. Sao lưu/di chuyển file trước khi bỏ binding cũ; không xóa bucket để thử. Bản Sites tùy chọn vẫn dùng binding R2 của Sites.

Lệnh deploy tự áp dụng toàn bộ drizzle/*.sql qua binding DB. Khi tìm thấy D1 đã có (hoặc đã ghim database_id), migration chạy trước bản code mới; nếu migration lỗi thì không deploy code mới. Với database hoàn toàn mới, script deploy để provision trước, tìm lại ID rồi chạy migration. Không sửa hoặc xóa migration đã áp dụng. Có thể lưu các ID resource thực tế vào GitHub để ghim kho và bỏ qua bước tra cứu ở các lần build sau.

Chỉ cho nhánh production triển khai production. Tắt automatic deploy nhánh thử nghiệm, hoặc dùng Worker/D1/KV riêng cho staging; không chạy migration production từ preview PR.

## 3. Thiết lập đăng nhập GitHub

Sau lần deploy đầu, lấy URL Worker thực tế, ví dụ https://valley-chibi-studio.<account>.workers.dev. App chưa cho đọc/ghi dữ liệu khi chưa cấu hình đăng nhập.

GitHub → Settings → Developer settings → OAuth Apps → New OAuth App:
- Application name: Valley Chibi Studio
- Homepage URL: URL Worker thực tế
- Authorization callback URL: URL Worker + /auth/callback

Trong Cloudflare Worker → Settings → Variables and Secrets, đặt:
- PUBLIC_ORIGIN: URL Worker thực tế, HTTPS, không có dấu / cuối hoặc đường dẫn.
- GITHUB_ALLOWED_LOGINS: GitHub username của bạn, ví dụ vanhungtq. Nhiều người thì cách nhau bằng dấu phẩy.
- Hoặc GITHUB_ALLOWED_IDS: numeric GitHub user ID. ID ổn định khi đổi username.
- GITHUB_CLIENT_ID: Client ID của OAuth App — lưu dạng Secret.
- GITHUB_CLIENT_SECRET: Client Secret — lưu dạng Secret.

Nhánh main của repo này đã đặt `PUBLIC_ORIGIN=https://valley-chibi-studio.vanhungtq1.workers.dev` và `GITHUB_ALLOWED_IDS=132463035` (tài khoản `vanhungtq`). GitHub ID được dùng để quyền truy cập không phụ thuộc việc đổi username. Nếu cài sang tài khoản hoặc Worker khác, thay hai giá trị này trước khi deploy. Callback của bản hiện tại là `https://valley-chibi-studio.vanhungtq1.workers.dev/auth/callback`. Hai Secret OAuth vẫn nhập riêng trong Cloudflare; không ghi vào cấu hình Git.

Không nhập secret vào GitHub, hình chụp công khai hoặc chat. Không cần khóa API mô hình.

PUBLIC_ORIGIN và allowlist cũng có thể ghi vào vars trong wrangler.jsonc. Repo dùng `keep_vars: true` để giữ các biến Runtime thêm trong Dashboard nhưng chưa có trong cấu hình nguồn. Giá trị đã khai báo trong `vars` vẫn được áp dụng từ GitHub, nên nếu đổi PUBLIC_ORIGIN hoặc allowlist ở Dashboard cần đồng bộ lại các trường tương ứng trong repo. Hai thông tin OAuth chọn đúng loại **Secret**, lưu ở Worker Runtime → Settings → Variables and Secrets, không ở Build variables và không đặt trong `vars` của Git.

Nếu `/healthz` chuyển từ `authConfigured: true` sang `false` sau một lần deploy, kiểm tra và lưu lại `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET` dưới loại Secret rồi Save/Deploy. Giữ nguyên GitHub OAuth App và callback đã tạo; không gửi giá trị Secret vào chat.

Nếu dùng custom domain, cập nhật PUBLIC_ORIGIN và GitHub OAuth callback cho domain mới. Dùng một origin chính thức; hostname khác bị từ chối. Không đặt Cloudflare Access login HTML trước /mcp, /oauth/*, /authorize hay /.well-known/* vì MCP client cần tự thực hiện OAuth. Bản này tự xác thực các endpoint đó.

Đăng nhập giao diện bằng nút Đăng nhập. Chỉ GitHub user trong allowlist truy cập được dữ liệu; mỗi numeric ID có dự án và file riêng. Cookie đăng nhập là HttpOnly/Secure và dữ liệu API có kiểm tra Origin cho thao tác ghi.

## 4. Dùng loại MCP nào?

Loại: Remote MCP.
Transport: Streamable HTTP, stateless.
URL: https://<domain-worker>/mcp
Authentication: OAuth 2.1, authorization code + PKCE S256.
Client registration: hỗ trợ CIMD và Dynamic Client Registration.
Scope: studio:access; offline_access cho duy trì kết nối.

Không dùng stdio cho app web này. GET /mcp trả 405 là hợp lệ: server nhận POST JSON-RPC và trả application/json; không cần một luồng SSE thường trực.

ChatGPT/Codex → khu vực quản lý app/plugin hoặc MCP server → thêm server riêng → nhập URL /mcp, chọn OAuth nếu có yêu cầu. Tên mục cụ thể tùy tài khoản và giao diện; khả năng thêm custom MCP cần được bật cho tài khoản/workspace. Khi kết nối, Xưởng hiện màn hình cho phép trước, sau đó đăng nhập GitHub. Dùng cùng tài khoản GitHub với giao diện để thấy cùng dự án.

Nếu giao diện yêu cầu Client ID/Client Secret của MCP, dùng đăng ký client phù hợp với cấu hình đó; không nhập GitHub Client Secret vào ô MCP. GitHub OAuth App là bước đăng nhập phía server, khác client OAuth ChatGPT/Codex. Bản này công bố endpoint /oauth/register để client hỗ trợ DCR đăng ký tự động và công bố CIMD cho client hỗ trợ.

Các endpoint discovery:
- /.well-known/oauth-protected-resource
- /.well-known/oauth-authorization-server
- /authorize
- /oauth/token
- /oauth/register

Trong ảnh Zero Trust → Access controls → MCP Portals:
- Tab MCP servers dùng để khai báo/quản lý một server MCP đã chạy.
- Server portals dùng để gom nhiều server và áp chính sách tập trung.
- Một Xưởng riêng có thể kết nối thẳng URL /mcp vào ChatGPT/Codex, chưa cần tạo Portal. Portal là lớp bổ sung tùy chọn, cần kiểm tra luồng OAuth riêng nếu sử dụng.

Plugin Sites đã cài vẫn trỏ về Site cũ. Bản Cloudflare cần kết nối MCP riêng; không tự thay đổi endpoint của plugin Sites.

### Dùng nhiều tài khoản Codex với cùng Xưởng

Đổi tài khoản Codex chỉ cần kết nối lại cùng URL MCP và cấp quyền bằng cùng GitHub chủ Xưởng. Dữ liệu giữ ở Cloudflare; không cần tạo Worker/D1/KV hoặc GitHub OAuth App khác. Chọn **Kết nối Codex** để sao chép URL và yêu cầu tiếp tục có ID đầu việc. Với việc đang chạy, chủ dự án có thể bấm **Bàn giao sang Codex khác**: phiên cũ mất claim, tiến độ/file giữ lại, phiên mới nhận token mới ngay. Kết quả tuân theo chế độ thủ công hoặc tự động bạn chọn trong Xưởng.

[Hướng dẫn chuyển tài khoản](RESUME_CODEX.vi.md) và [prompt tiếp tục](CODEX_RESUME_PROMPT.vi.md) phân biệt kết nối lại, sửa mã GitHub và tạo Xưởng mới. Chat/file chưa đồng bộ không tự chuyển tài khoản. Mỗi tài khoản/workspace cần hỗ trợ custom MCP; không sao chép thông tin đăng nhập giữa các tài khoản.

## 5. Kiểm tra sau cài

Mở /healthz: databaseReady, filesReady, oauthStorageReady và authConfigured cần là true. Kiểm tra chỉ phản ánh cấu hình/schema, không thay thế đăng nhập thật.

Đăng nhập website, thêm một tư liệu nhỏ và tạo một đầu việc. Trong ChatGPT/Codex đã kết nối MCP, yêu cầu studio_get_project và studio_list_tasks. Nhận đúng đầu việc, báo tiến độ, lưu file, nộp kết quả. Giao diện thăm dò mỗi 5 giây khi đang mở để cập nhật chibi. Mặc định kết quả chờ bạn duyệt; bật Tự động duyệt & chuyển bước để máy chủ duyệt và Codex tiếp tục đầu việc kế tiếp.

AI không tự chạy khi đóng ChatGPT. Cloudflare chỉ lưu, giao việc và đồng bộ; ảnh storyboard dùng công cụ tạo ảnh của phiên ChatGPT/Codex.

## 6. Dữ liệu cũ và giới hạn

Dữ liệu Sites/R2 cũ không tự chuyển sang Cloudflare của bạn. Không sao chép DB hoặc upload giữa tài khoản khi chưa xác nhận. JSON backup không chứa file nhị phân; namespace owner mới là github:<numeric-id>, khác ID Sites, nên không nhập nguyên metadata file cũ như thể file đã có. Cần tải lại file và gắn lại các liên kết hoặc thực hiện migration dữ liệu riêng.

Upload giao diện Cloudflare KV: 20 MiB/tệp. MCP đọc file: 5 MB/lượt. MCP nộp artifact: 1 MB/tệp. Video lớn hơn lưu URL nguồn và ảnh từng shot. Metadata dự án vẫn lưu dạng JSON trong D1; bản tổ chức triển khai này chưa chuyển thư viện sang tìm kiếm FTS/phân trang riêng.

## 7. Chạy và kiểm tra cục bộ

npm ci
npm run cf:migrate:local
cp .dev.vars.example .dev.vars

Điền GitHub OAuth App thử nghiệm vào .dev.vars; không commit. Đặt PUBLIC_ORIGIN=https://localhost:8787, allowlist thử nghiệm trong vars hoặc .dev.vars, callback cùng origin + /auth/callback. OAuth cookie yêu cầu HTTPS; lệnh npm run dev bật HTTPS cục bộ. Cần tin chứng chỉ phát triển để thử đăng nhập; app GitHub thử nghiệm nên tách khỏi production.

npm run dev
npm test
npm run check
npm run cf:check
npm run build:sites  # Chỉ khi cần đóng gói cho Sites cũ

## 8. Lỗi khi xác nhận OAuth

Nếu màn hình xác nhận MCP báo “Yêu cầu thay đổi dữ liệu phải đến từ chính giao diện Xưởng”, cập nhật bản `main` mới rồi bắt đầu kết nối lại từ ChatGPT/Codex, không gửi lại form cũ. Form OAuth dùng `Referrer-Policy: same-origin` để giữ Origin hợp lệ; CSP chỉ cho redirect qua GitHub và origin callback đã được OAuth provider kiểm tra. Không sửa CSRF để chấp nhận Origin thiếu, `null` hoặc khác nguồn. Kiểm thử Chromium thật nằm ở `npm run test:browser:oauth`; GitHub trong bài kiểm thử được giả lập, không thay thế việc đăng nhập thật của chủ Xưởng.
